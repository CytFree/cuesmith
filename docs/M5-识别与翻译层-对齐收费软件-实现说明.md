# M5 — 识别与翻译层对齐收费软件（词级 ASR / 术语表 / 上下文翻译 / 译后精简 / 排版时序）

> 状态：**已完成**。新增 `asr` / `translate` 两个子命令与 `glossary` / `condense` 两个模块；
> 全量测试 **397 个**、一键回归 **21 项**全绿（`work/regression-m5/regression.json`，20.2s）。
> 实测素材：用户提供的 2 分钟 YouTube 英文播客（`work/user-en/seg.mp4`，已取得使用授权）。

## 1. 为什么做这一轮

用户原话：**"我们要做，那就要对齐收费软件。除非有特别大的成本，其他的我们都可以对齐。"**
M0–M4 已经把"能不能跑通"解决了，但 en→zh 的字幕"读起来不通顺"，和收费软件差在
识别与翻译这两层。收费软件的完整链路是五层：

| 层 | 收费软件的做法 | M4 之前 | M5 |
|---|---|---|---|
| ① ASR | 大模型 + **词级时间戳** + **热词偏置** + 独立标点模型 | 底座段级 SRT；12s 上限硬切 | ✅ `asr`：词级 + 热词 + VAD |
| ② 断句 | **语义断句**（按词级时间戳重切，不在硬上限处切） | `merge` 只合并不拆 | ✅ 句末/长停顿/超长才切 |
| ③ 翻译 | **上下文**（前后句一起译）+ **术语表/禁译表** + 风格一致 | 逐句免费 MT | ✅ 段落上下文 + 术语占位 |
| ④ 排版 | 折行 + 按 CPS 切条 + **时间按语速分配** | `--wrap` 已做，但时序按字符数 | ✅ 按语速折算 + 专名不拆行 |
| ⑤ 配音 | isochrony + **脚本改写压缩** | atempo/吸收/调速 | ✅ 译后精简（rule/trim/LLM 三档） |
| ⑥ 术语 | glossary + 禁译表 | 无 | ✅ 占位保护（翻译前置换、翻译后还原） |

**成本过高、本轮明确不做**（见 §8）：说话人分离、声音克隆、BGM 人声分离、唇形同步。

## 3. ASR 直连（第 ①② 层）

### 3.1 为什么不用底座的段级 SRT

M4 的 `merge` 只能"合并不拆分"，遇到 12 秒上限时仍会把句子砍断。实测底座产出的
`merge-v3/merged.srt` 里存在这样的 cue：

```
1  00:00:00,000 --> 00:00:03,340   you're talking to an AI, and the AI knows what it's capable of, and it could
```

句尾没有标点、以 "and it could" 结束——翻译只能猜这句话还没完。根因是底座 ASR 只给段级
时间戳，`merge` 到 12s 必须 flush。拿到**词级时间戳**后，切条可以做在真正的句末/长停顿上。

### 3.2 环境隔离（版本敏感）

faster-whisper 依赖 ctranslate2，后者 4.8.x 在本机 Windows 上访问违例（M0 已踩）。
所以模型只在底座 venv 里跑（`--asr-python` 自动发现
`spike/pyvideotrans/.venv/Scripts/python.exe`），主包保持"标准库 + ffmpeg"：

```
submatrix asr ──subprocess──> asr_worker.py（底座 venv + ctranslate2 4.5.0）
      │                              │
      └────── asr-worker.json <──────┘   words[] / segments[] / info
```

模型自动发现顺序：`--model` → `SUBMATRIX_ASR_MODEL` →
`spike/pyvideotrans/models/models--Systran--faster-whisper-small` → 其它常见目录。
找不到时直接报错并给出 `--model` 用法，不会去联网下载（本机 HF 被墙）。

### 3.3 切条规则

只在四种情况下切，不为凑条数切：

1. 词尾是句末标点（`。！？.!?…`）；
2. 与上一词的间隔 ≥ `--pause`（默认 0.5s，静音/换气）；
3. 本条累计时长 > `--max-duration`（默认 7s）；
4. 本条累计字符 > `--max-chars`（默认 200）。

之后把 < `--min-duration`（0.4s）的碎片并到相邻条（不超过上限），并丢掉 `[Music]`/`♪`
这类非语音段。产物：

- `source.srt`：字幕条
- `words.json`：全部词级时间戳（可做二次断句/对齐）
- `asr.json`：语言、置信度、词/段/条数、语音时长、RTF、热词、配置

### 3.4 实测（2 分钟播客，AMD 780M / CPU int8）

| 指标 | 数值 |
|---|---|
| 音频时长 / 语音时长 | 120.0s / 111.7s |
| 词 / 模型段 / 字幕条 | 475 / 27 / **30**（平均 3.72s） |
| 耗时 / RTF | **37.6s / 3.19×实时**（复跑 2.15–3.19×，取决于热词与 min-duration） |
| 语言置信度 | 1.00（en） |
| 热词 | AI、OpenAI、Blender、Astra（4 个） |

30 条**全部**以句末标点收尾（如 `...what it's capable of.` / `...something more complex.`），
`Blender`、`Astra` 等专名识别正确——这是 M4 段级输出做不到的。另外两处刻意设计：

- **句首大写 / 独立 `i` → `I`**（whisper 段首小写是客观现象，字幕要按句首大写显示）；
- **短于 0.8s 的条并入相邻条**（`Here's an idea.` 0.68s 会并进下一句，避免一闪而过）。

## 4. 翻译编排（第 ③⑥ 层）

### 4.1 渠道（引擎不自建，只做编排）

| 渠道 | 用途 | 说明 |
|---|---|---|
| `microsoft`（默认） | 免费端点，无需 key | 零成本；实测 ~10s/请求 |
| `openai` | OpenAI 兼容 chat/completions | 上下文翻译 + 译后精简质量最好；实测接 **DeepSeek** |
| `command` | 任意外部命令 | `{input}`/`{output}` 为 JSON 数组文件 |
| `echo` | 离线回显 | 只用于 CI/回归跑通管线 |

LLM 配置全部走环境变量，避免 key 进命令行历史：

- `DEEPSEEK_API_KEY`：设置后自动用 DeepSeek（`https://api.deepseek.com/v1` + `deepseek-chat`）；
- 或 `SUBMATRIX_LLM_API_KEY` + `SUBMATRIX_LLM_BASE_URL` + `SUBMATRIX_LLM_MODEL`（任意 OpenAI 兼容端点）；
- 也兼容 `OPENAI_API_KEY`。

```powershell
$env:DEEPSEEK_API_KEY = "sk-..."       # 只放在当前 shell，不写入仓库
python -m submatrix translate --src asr/source.srt --out mt --provider openai `
  --src-lang en --tgt-lang zh --glossary glossary.tsv --condense --condense-mode llm
```

> 账单透明：`translate.json` 的 `config.llm` 会记录 `calls / prompt_tokens / completion_tokens /
> total_tokens`，跑完直接能算钱。密钥由用户提供、只存在于环境变量，不进产物、不进报告。

### 4.2 处理流水线

1. **源文清洗**：`actually,i could do` → `Actually, i could do`（补标点后空格）；独立
   `i` → `I`；去标点前空格；中文拍平多余空白。ASR 噪声会直接拉低机翻质量。
2. **整句化**：半句不翻；英文里"下一条以小写开头"的假句号并回上一句。
3. **段落上下文（按句子传）**：相邻 cue 编段（≤4 条、≤480 字、间隔 ≤1.5s），把整段**所有
   句子**作为 JSON 数组放进**一个请求**：LLM 能看到整段上下文，同时被要求"返回同样多的
   句子"。返回后按"这个句子属于哪条 cue"精确拼回，对齐不靠猜。
4. **对齐策略的演进**（M5 踩坑记录）：
   - v1 按字数比例切整段译文 → 长短句一不匀就整条漂一个 cue（"右？"被单独塞给一条）；
   - v2 按译文语速把句子铺到时间轴 → 好一些，但中文/英文句子长度比例不同仍会漂；
   - v3（最终）**一句对一句**：句子是翻译的最小单位，归属关系天然精确。代价是 LLM
     必须遵守"句子数不变"，实测 DeepSeek 8 段全部遵守。
5. **术语表**：翻译前把术语换成 `{{G0}}` 占位符（实测该形态在微软端点上原样保留），
   翻译后换回指定译法；机翻吃掉占位符会记 `placeholder_lost` 并告警。
6. **译后精简**（可选）：目标 CPS 超限时按 `rule`（删"那么/其实/就是说"等口头禅）、
   `trim`（从最后一个分句截断，会丢信息、报告逐条标出）、`llm`（重写压缩）处理。
   **防偷工减料**：LLM 改写若删掉了整句，会被"句子数不得减少"规则拒绝（实测它确实会为了
   达字数直接丢一句），宁可超限也不悄悄丢信息。
7. **中文空格归一**：占位符还原/LLM 输出可能留下 "一个 演示文稿"，统一去掉中文字符间空格
   （中英之间保留，如 "和 AI 对话"）。
8. **报告**：`translate.json` 记录提供商、上下文配置、段落数、回退条数、术语丢失数、
   精简动作、CPS（精简前/后）、LLM token 用量、耗时，并把超限条数写成 warning。

### 4.3 术语表格式

```tsv
# source<TAB>target[<TAB>keep]
Blender	Blender	keep
large language model	大语言模型
AI	AI	keep
```

也支持 JSON（`{"terms":[{"source":"AI","keep":true}, ...]}` 或 `{"AI":"AI"}`）与
一行一个禁译词的 `.txt`。匹配规则：拉丁词按词边界（`AI` 不会命中 `said`）、默认忽略大小写；
中文按子串；多个术语重叠时长者优先。同一个术语表可直接喂给 `asr --hotwords-file`。

### 4.4 实测：免费 MT vs DeepSeek（同一素材，同一术语表）

| 指标 | `microsoft`（免费） | `openai` → DeepSeek |
|---|---|---|
| 上下文 | 句级（端点本身不支持跨行上下文） | 整段句子数组，真正的段落上下文 |
| 翻译耗时 | **79.0s** | 131.2s（13 次请求） |
| token 用量 | 0 | 2454（prompt 1934 / completion 520） |
| 中文 CPS（句子级 30 条） | 6.88 → 6.71，超限 6/30，峰值 12.14 | 7.08 → **6.82**，超限 **1/30**，峰值 11.65 |
| 排版后（49–50 条） | 49 条，超限 8，峰值 13.8 | 50 条，超限 **2**，峰值 13.2 |
| 译后精简 | rule（删口头禅） | LLM 重写 4 条；1 条被"丢句检查"拒绝 |
| 成本 | 0 | 约 ¥0.01 量级 / 2 分钟素材（2454 token，按官方价目） |

同一句对照（左侧为免费 MT 的"每个词都翻了但没人这么说话"）：

| 原文 | 免费 MT | DeepSeek |
|---|---|---|
| it's not theoretical with thoughts. | 不是用思维理论的。 | 并不是理论上的想法。 |
| You want something you can talk to that can solve problems... | 你需要一个可以沟通、能解决问题…的人 | 你想要一个能与之交流、能解决问题…的东西 |
| Right. I'm pretty good at writing software. | 我写软件还挺不错的。 | 对吧。我写软件还挺不错的。 |
| Actually, I could do even more, right? | 我还能做更多。 | 其实我能做得更多，对吧？ |

**结论**：免费端点够用、零成本；LLM 渠道更顺，且更容易把 CPS 压进规范。默认仍是
`microsoft`（不花钱），要发布级质量时切 `--provider openai`（DeepSeek key 即插即用）。

## 5. 排版时序与折行修复（第 ④ 层）

M4 的 `--wrap` 已经能折行/切条，但在真实快语速素材上暴露出五个问题，M5 全部修掉：

| # | 问题 | 根因 | 修复 |
|---|---|---|---|
| 1 | 中文 CPS 忽高忽低（有的条 14、有的条 3） | 时间按 `max(英文字符数, 中文字符数)` 分配，被更长的英文带偏 | 改为**按译文所需时长分配**：观众读的是译文，原文只提供"这段语音占多久"的外框 |
| 2 | 原文第 i 段和译文第 i 段内容对不上 | 两侧各自按自己的容量折行，段落边界不一致 | 两侧用**同一组时间进度分数**切文字，优先落在标点后 |
| 3 | 极端条 276ms / 39.9 CPS | 先按比例分、再把过短段抬到最小值，被抬的时间是从别的段硬扣的 | 先给每段预留最小值，再分配剩余时间（并保证总和 == 原时长） |
| 4 | 6.8s/40 字的一条被切成 5 条"逗号碎片" | 段数按"分句单元数"估，长句会被数成很多段 | 段数按 `max(容量需求, min(两侧句子数))` 估，即"一句一条"但不过度切分句 |
| 5 | `Blender` 被切成 `Blend`/`er`、`B lender` | 中文按字符折行；切条时在字符中点硬切 | 折行按 token、切点避开拉丁词内部；中文标点容差放宽、英文收紧 |

同一段素材前后对比：

| 指标 | M4 | M5（免费 MT） | M5（LLM） |
|---|---|---|---|
| 交付字幕条数 / 平均时长 | 57 条 / 2.1s | 49 条 / 2.3s | 50 条 / 2.2s |
| 中文 CPS 超限 | 11 条（峰值 **20.6**） | 8 条（峰值 13.8） | **2 条（峰值 13.2）** |
| `line_width` 告警 | 1 | **0** | **0** |
| `line_count` 告警 | 0 | **0** | **0** |
| 专名完整性 | `B` / `lender` 断行 | **Blender 完整** | **Blender 完整** |

> 英文侧仍有 30–32 条 CPS 告警：这段播客语速约 **21 CPS**，本身就超过 20 CPS 规范上限。
> 中文侧剩下的 1–2 条也是"原文语速太快、译文内容装不进这个时间窗"，工具如实报告，不假装修好。
> 想再压只能：`translate --condense`（trim/LLM 重写）或延长显示时间。

## 6. 端到端实测（2 分钟英文播客）

两条翻译链路都跑通了，产物分别留档：

| 阶段 | 免费 MT 链路（`--provider microsoft`） | LLM 链路（`--provider openai` → DeepSeek） |
|---|---|---|
| 探测 | 无字幕轨 → `route_to_asr` | 同左 |
| 识别 `asr` | 120s → 475 词 / 30 条；37.6s（3.19×实时） | 同左 |
| 翻译 `translate` | 79.0s；CPS 6.88→6.71，超限 6/30，峰值 12.14 | 131.2s；CPS 7.08→6.82，超限 **1/30**，峰值 11.65；13 次请求 / 2454 token |
| 排版 `build --wrap` | 30 → 49 条；中文 CPS 超限 8，行宽/行数 0 | 30 → **50 条**；中文 CPS 超限 **2**，行宽/行数 0 |
| 配音（句子槽位 `dub`） | 30/30；atempo 6、吸收 6、**人工 4**；33.9s（+40%） | 30/30；atempo 15、吸收 1、**人工 4**；34.6s（+30%） |
| 配音（排版槽位） | 47/49（2 条网络）；atempo 15、吸收 6、**人工 12**；70.7s（+30%） | —（结论同左，槽位碎了人工必涨） |

> 另试过 `--condense-mode trim`：中文 CPS 超限从 6/30 降到 **4/30**，代价是 2 条共截断
> 39 字（报告逐条标出"需人工抽检"）。默认不开启 trim，就是为了不悄悄改用户的意思。
> LLM 精简也不会"为达字数删句"——删整句会被拒绝（见 §4.2 第 6 条）。

### 6.1 译文质量对照（同一素材，M4 vs M5）

M4（底座段级 ASR + 逐句机翻）：

```
...我认为现在Astra在B lender方面已经非常出色了...
```

M5（词级 ASR + 热词 + 上下文翻译 + 术语表）：

```
...我认为现在Astra在Blender和3D建模方面都非常出色。...
```

其它可见改善：

- `right?` 不再被单独翻成 `右？`（上下文译成 `对吧？`）；
- 段落内不再整条错位（整段句子一次翻译、一句对一句拼回，短 cue 拿到自己的译文）；
- 术语 `AI`/`Blender`/`OpenAI` 全片译法一致，占位符丢失 0；
- 句首大写、独立 `i`→`I`、短于 0.8s 的碎片条自动合并。

## 7. 配音与字幕要解耦（实测结论）

字幕**按阅读体验切条**（49 条、平均 2.3s），配音**按语义句子给槽位**（30 条、平均 3.7s）。
拿排版后的字幕直接配音，槽位被切碎，人工处理条数明显上升：

| 配音槽位来源 | 条数 | 平均槽位 | atempo | 吸收 | 人工 | 耗时 |
|---|---|---|---|---|---|---|
| 排版后字幕（49 条，+30%） | 49 | 2.27s | 15 | 6 | **12** | 70.7s（47/49，2 条网络） |
| 句子级译文（30 条，+40%，免费 MT） | 30 | 3.72s | 6 | 6 | **4** | 33.9s |
| 句子级译文（30 条，+30%，LLM） | 30 | 3.72s | 15 | 1 | **4** | 34.6s |

> 结论：**翻译产物（句子级）配完音，再用 `build --wrap` 生成发布字幕**；两份产物共用同一条
> 翻译，时间轴各自最优。收费软件也是这么分的（dub script 与 subtitle track 是两条轨）。
> 人工处理条数 12 → 4，就是这个结论最直接的证据。

## 11. M5.1 精修（用户第二轮要求：auto 默认 + LLM 打磨 + 术语不可丢）

用户口径：① `auto` 就是默认模式；② 要精确结果就用 LLM 这条路；③ BGM 也要做（见 M6）。

### 11.1 精简默认开启（auto）

- `translate` 不加任何参数就会对**超过目标 CPS** 的条目做精简：有 LLM 用 LLM 重写，
  没有 LLM 就 `rule`（只删口头禅）→ 必要时 `trim`（截分句，**会丢信息**）。
- `--no-condense` 关闭；`--condense-mode rule|trim|llm` 可强制指定策略。
- 报告新增 `summary.condense.needs_review`：逐条列出被 `trim`/LLM 改写过的 cue
  （cue 号、前后字数、改后文本），告警里也会提示"需人工抽检"。**不再悄悄改**。

### 11.2 术语不可丢（硬约束）

实测踩到：第 4 条译文 `我有个主意。我能做一个演示文稿，一个电子表格。` 超 CPS 11.2，
`trim` 一截就把「一个电子表格」删掉了——而它是术语表强制译法，**删了就不可恢复**。

修复：`condense` 接受 `keep` 列表（术语译法/禁译名），

- `trim` 不删含术语的分句；删不动就**宁可超 CPS**，报告如实标出；
- LLM 重写后若术语丢失，判定为无效重写，退回保守路径。

结果：本轮最终产物中文 CPS 超限 **1/49**，那 1 条正是"为保住「电子表格」主动超限"，
报告里能对上账（`needs_review` 第 4 条，12.5 CPS）。这是**有意的取舍**，不是漏修。

### 11.3 LLM 渠道打磨（`--provider openai`）

| 改进 | 说明 |
|---|---|
| 术语对照表入提示 | 占位符 `{{G0}}` 对免费 MT 是"不可翻译符号"，对 LLM 则附上"原文→应输出"，模型才能写出语法正确的上下文 |
| 每行字数预算 | 按"该句所在 cue 时长 × 目标 CPS"给出 `max_chars` 数组，模型在预算内选更紧凑的说法（均值 CPS 7.08 → 6.74→6.42） |
| 条数兜底 | 模型偶尔把相邻两行并一行：同请求强调条数重试一次；仍不对就**对半拆批**重翻，不再整批失败 |
| 双轮审校 `--llm-review` | 第一轮成品进第二轮再审（默认 2 轮，某轮零改动即收敛）。只允许改"误译/否定/主语/时态/数字/术语/丢失谓语的碎片" |
| 改动留痕 | `translate.json` 的 `summary.review.changes` 记录每条 `before/after`，可逐条核对审校到底改了什么 |

### 11.4 本轮实测（同一素材，DeepSeek，2 轮审校）

| 指标 | M5 首版（`--condense-mode llm`） | M5.1（默认 auto + hints + 2 轮审校） |
|---|---|---|
| 调用 / token | 13 次 / 2454 | 30 次 / 9885（prompt 8496 / completion 1389） |
| 耗时 | 131.2s | 298.2s（多出的是两轮审校） |
| 中文 CPS（句子级 30 条） | 7.08 → 6.82，超限 1/30，峰值 11.65 | 6.74 → **6.42**，超限 **1/30**，峰值 11.17 |
| 排版后（49 条） | 50 条、超限 2、峰值 13.2 | 49 条、超限 **1**、峰值 12.5（术语保护所致） |
| 精简 | LLM 4 条 | LLM 5 条 + 1 条"宁可超限" |
| 审校 | 无 | 2 轮，改 2 条（"造"→"做"、修回"比我认识的任何人都强"） |
| 成本 | 约 ¥0.01 | 约 ¥0.03 量级 |

### 11.5 仍然做不到的（如实记录）

- **LLM 不是确定性的**：temperature=0 时同一输入连跑两次仍有措辞差异，个别句子
  （"That's not the AI we were promised"）一次对一次错；两轮审校能拦住一部分，不保证全拦。
  发布前仍需按 `needs_review` 人工抽检。
- **口语病句照样难**："it's not theoretical with thoughts" 两轮审校都没敢动，仍是直译。
- **trim 仍可能丢措辞**：只保证不丢术语、不删整句；细节改写仍需人看。
